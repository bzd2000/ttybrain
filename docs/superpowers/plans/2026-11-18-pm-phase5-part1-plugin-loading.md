# pm phase 5, part 1: plugin loading and alignment — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** One loader and one manifest for built-in and external plugins; built-ins import only `@pm/api` / `@pm/api/tui` and can be switched off; external plugins load from `~/.pm/plugins` (folders and npm), are built with `pm plugin build`, managed with `pm plugin add|remove|enable|disable|new`, and fail without taking pm down.

**Architecture:** A new kernel module `src/kernel/loader.ts` reads `package.json` manifests from pm's built-in folder (`src/plugins`, or `dist-node/plugins` on Node) and from `paths.plugins`, imports the logic entries, and hands `bootKernel` a list of candidates with their source; the host's existing ordering, version checks and isolation then apply to all. The TUI loads each `ok` plugin's `pm.tui` entry. External plugins reach pm's module instances through shims that read `globalThis.__PM_MODULES__`, generated by `pm plugin build`.

**Tech Stack:** TypeScript, Bun 1.4 and Node 26.4+, OpenTUI + Solid, Kysely over SQLite, Babel (`@babel/core`, `@babel/preset-typescript`, `babel-preset-solid`, `babel-plugin-module-resolver`).

**Spec:** `docs/superpowers/specs/2026-11-18-pm-phase5-plugins-design.md` (phase 5 design; wins for this phase), with `docs/superpowers/specs/2026-11-13-pm-design.md` §3 for the plugin model. Read `docs/architecture.md` before any kernel or plugin change.

## Global Constraints

- Both runtimes must keep working: every task ends with `bun test`, `bun typecheck` and `bash scripts/smoke-node.sh` (last line `smoke ok`) green.
- Use only ESM; keep relative imports in `src/` extensionless; no `Bun.*` outside `src/kernel/db/sqlite.ts`.
- Logic and kernel code (outside `src/kernel/tui/`) never statically import `solid-js`, `@opentui/*`, `@pm/api/tui` or anything under `src/kernel/tui/` (`tests/logic-ui-split.test.ts`).
- Plugins' non-test files reach the kernel only through `@pm/api` and `@pm/api/tui` (Task 1 adds the test).
- Shared module names, exactly: `@pm/api`, `@pm/api/tui`, `solid-js`, `solid-js/store`, `@opentui/solid`, `@opentui/core`.
- Manifest: `package.json` with `"type": "module"`, `main` (logic entry, default export a `PluginDef`), `"pm": { "plugin": true, "id": "<id>", "tui"?: "<entry>" }`; `version` equals `PluginDef.version`; `pm.id` equals `PluginDef.id`.
- Sources, exactly: `"built-in" | "folder" | "npm"`; load order built-ins, then folders by directory name, then npm dependencies by package name; then the host's `requires` sort.
- Disabled plugins are never imported (their code does not run).
- An external plugin whose id equals a built-in's fails with `plugin id "<id>" is taken by a built-in plugin`.
- External migrations run with the trigger ban (`MigrationRunner.run(id, migrations, true)`); built-ins with `false`.
- Message texts fixed by the design or this plan are used verbatim.
- CLI conventions (`--json`, exit codes 0/1/2/3, hints) as in `docs/architecture.md`; tests use `runCli` and a fixed clock, never the real clock.
- Disabling keeps a plugin's data; there is no purge for built-ins.
- Git: one commit per task (more is fine), messages `feat(…)`/`fix(…)`/`docs: …`, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Plan rulings (decisions this plan adds to the design)

- **R1. `pm.id` is required** in every manifest, so a disabled plugin's id is known without importing it (design §5 left this open). The loader fails a candidate whose `pm.id` differs from `PluginDef.id`.
- **R2. Timeouts:** importing an external candidate and an external `activate` are each raced against 5000 ms; on timeout the plugin fails with `<id>: timed out after 5000 ms while <importing|activating>`. Built-ins have no timeout.
- **R3. A tui `activate` must be synchronous.** If it returns a thenable, the part fails with `<id>: tui activate must be synchronous`, its registrations are removed, and the rejection is swallowed.
- **R4. Shims are generated from what the plugin imports**, not from the host's full export list: the build never has to import UI modules. Each shim checks, at load, that every imported name exists on the host module, and throws `rebuild the plugin with this pm (missing export "<x>" from "<name>")` otherwise. A namespace import (`import * as x`) or `export *` of a shared module fails the build with `<file>: use named imports from "<name>"`.
- **R5. `pm plugin remove` is destructive** (needs `--yes`) because it deletes a folder or uninstalls a package. `--purge-data` additionally drops the plugin's data.
- **R6. Installer choice:** `npm` when it runs (`npm --version` exits 0), else `bun add --cwd` when running under Bun, else an error `pm plugin add needs npm on the PATH`. `PM_PLUGIN_INSTALLER=npm|bun` forces one (used by tests to cover both).
- **R7. Built-in lists for tests** move to `tests/builtins.ts` (static imports, test-only). `src/plugins/index.ts` and `src/plugins/tui.ts` are deleted.

## Review Focus

1. **A `~/.pm/plugins` that is messy** (stray files, a folder without `package.json`, invalid JSON, an npm dependency that isn't a pm plugin, a dependency listed but not installed): pm starts, ignores non-plugins, lists the broken ones as failed. Tests in Task 2.
2. **A plugin that hangs or rejects during import or activate**: pm still starts within the timeout and lists it failed. Tests in Tasks 2 and 3 (R2), Task 4 (R3).
3. **Disabling a plugin that others require** (`projects` with `meetings` on): the dependants are listed as skipped with the reason, nothing crashes, and enabling restores everything with the data intact. Test in Task 5.
4. **A plugin built against a different pm** (missing shim export, or loaded outside pm): a clear "rebuild" or "load from pm" message, never a stack trace at startup. Tests in Task 7.
5. **Paths with spaces and symlinks** (`PM_PLUGINS="/tmp/my plugins"`, an `npm install <folder>` symlink): loading and `pm plugin remove` work. Tests in Tasks 2 and 8.
