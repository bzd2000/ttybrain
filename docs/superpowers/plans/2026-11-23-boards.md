# Boards — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** A board meeting no longer belongs to a project: boards (`#MB` "Management board") are their own records in the meetings plugin, with series, meetings, a talk-list and linked actions.

**Architecture:** A small kernel change lets two record types (and tag types) share the `#` prefix, each resolving its own codes, with one shared code namespace. The meetings plugin adds the board table, record type, ops and CLI, makes `board` a subject type, and moves existing board-kind meetings off their project with a one-time data step. The TUI gets a Boards panel on screen 5 and a board view with Meetings and Talk tabs.

**Tech Stack:** TypeScript, Bun and Node 26, Kysely over SQLite, OpenTUI + Solid.

**Spec:** `docs/superpowers/specs/2026-11-20-ttybrain-meetings-actions-design.md` §5.7 (amendment 2026-11-23, boards), §5.1–§5.3, §3. No mock draws the board view: it follows the project Meetings and Talk tabs (`docs/superpowers/specs/2026-11-20-ttybrain-meeting-screens.html`, screens `project` and `board`).

## Global Constraints

- Board codes: 2–16 letters or digits, upper-cased on add and edit (like project codes); written `#CODE`. Project and board codes share one namespace: adding or renaming either refuses a code the other uses (`code "MB" is already used by the board #MB` / `… by the project #MB`, exit 3, with a hint).
- `#CODE` everywhere a project ref is accepted today resolves to whichever exists (project or board); places that need a project (project commands, a project link on an action, a talk item's project tag) refuse a board with a clear error, and vice versa.
- Kind `board` ⇔ board subject. Kind `project` needs a project; `1:1` a person (§5.1 otherwise unchanged).
- Nothing lost: existing board-kind meetings and series with a project subject move to a new board with that project's code and name; ids (`M-n`, `S-n`, `T-n`) unchanged; the project and its own data stay.
- Plugin isolation, Bun + Node, CLI conventions, look and feel as in the meetings plan; meetings stays 2.x (additive view and op changes) unless a published view changes shape (then 3.0.0 with readers' ranges).
- Bun and Node both green after every task: `bun run test`, `bun typecheck`, `bash scripts/smoke-node.sh`.

## Plan rulings

- **B1. Shared prefix in the kernel.** `RecordRegistry` and the tag registry accept several types for one prefix. `resolve("#MB")` asks each type sharing the prefix in registration order and returns the one that knows the code; two that both know it is a data error reported as such (the shared-namespace rule prevents it). `typeOfRef` returns the types for a prefix; callers that need one type pass it (`resolve(ref, { type })`). Suggestions for `#` merge both types' candidates.
- **B2. The namespace check** lives in each owner: meetings refuses a board code that `projects.project` (view) has; projects refuses a project code that `meetings.board` (new view) has — projects already reads meetings ^2.
- **B3. Data step** (meetings `ctx.upgrade("boards-from-projects")`): for every project that is the subject of a board-kind meeting or series, create one board with the project's name and the code `<CODE>B` (the shared namespace forbids reusing `<CODE>`; cut to 16 characters, and a digit added if it is taken), and move those meetings and series to it. The project keeps its code, talk items, actions and everything else; nothing is renamed. The step leaves a notice in `plugin list` and Help naming the new board, so the user can rename it (`board edit #BOARDB --code …`). In practice this touches few databases: existing meetings stay subject-less after the meetings upgrade until the user assigns one.
- **B4. Board view** is a record view (`#CODE` crumb, code cyan) with two bare tabs, Meetings (series panels, Past meetings, no Prep) and Talk; opened from screen 5's Boards panel or any `#CODE` of a board.
- **B5. Seeds:** `seedMeetings` uses a board `#BOARD` "Management board" instead of the BOARD project, so the mocks' `#BOARD` still reads the same; design frames that showed BOARD as a project change only where the project lists showed it.

## Review Focus

1. **`#CODE` that is a board where a project is needed** (`project show #MB`, `action add --project MB`, `talk add @anna "…" --project MB`, a project form's Project field): a clear "is a board, not a project" error with a hint, never a crash or a silent wrong record. Test in Task 1/2.
2. **Code clash on rename** (`project edit CRM --code MB` while board `#MB` exists, and the reverse; case-insensitive): refused, nothing changed. Test in Task 2.
3. **Upgrade of a database whose board meetings sit on a project** (series, occurrences, held meetings with notes, talk_kept, linked actions): all move to the new board with ids and history intact; the project keeps everything else; running the step again changes nothing. Test in Task 2.
4. **Quick capture `talk #MB …`** goes to the board's talk-list with the preview line naming the board and its next meeting; a `#CODE` that is neither goes to the inbox as before. Test in Task 3.
5. **80×24 board view and Boards panel:** codes and names whole. Test in Task 3.
