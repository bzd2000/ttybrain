> pm is now called ttybrain (2026-11-19); names below are updated.

Screen mockups: [`2026-11-13-pm-screens.html`](2026-11-13-pm-screens.html) (published at https://claude.ai/artifact/AtQuEpRLAjmtxaKEHXU4N2). Known differences: the home screen is called **Overview** (mockups say "Attention") and the project's first tab is called **Summary** (mockups say "Overview").

## 1. Purpose

A personal terminal tool for someone responsible for a portfolio of projects. It helps them:

1. manage and follow up the projects under their responsibility;
2. manage and follow up the team working on those projects;
3. manage and follow up the stakeholders of those projects;
4. prepare meetings and boards about those projects.

It also lets GitHub Copilot read and update the data, and it has an inbox for quick capture that Copilot can process.

**Users and scale.** One user. Data stays on that person's machine. There are no accounts, no sharing and no sync. Expected size: 20–30 active projects, about 20 active stakeholders, a team of about 10, and 5–10 board meetings. Nothing needs paging or indexes beyond the basics.

**Success looks like:**
- one screen that shows what needs attention today;
- capturing a thought takes about five seconds from any screen;
- a board pack comes from the data instead of being written by hand;
- Copilot can do routine updates safely.

**Starting point.** The repository already holds an OpenTUI + Solid starter that runs on Bun and on Node 26.4+ (see `CLAUDE.md`). Both runtimes must keep working. Nothing has to be imported: you start with an empty database.

## 2. Architecture

ttybrain is a small **kernel** plus **plugins**. Every feature area, the built-in ones included, is a plugin written against the same plugin API (§3). The kernel provides the plumbing and the three front ends.

```
src/kernel/            plugin host, registries, SQLite adapter, migrations runner, config,
                       record references, date parsing, typed errors, change sets
src/kernel/cli/        `ttybrain <thing> <verb>`: dispatches to commands registered by plugins
src/kernel/tui/        frame, screen switcher, forms, live refresh; renders screens, tabs
                       and panels registered by plugins
src/plugins/<id>/logic/ data, views, operations, CLI commands, tools, record types, reports,
                       guide: no UI imports (§3.1)
src/plugins/<id>/tui/   screens, tabs, panels, overlays, badges for the terminal UI
                       built-in ids: people, projects, meetings, inbox, assistant
src/bin/pm.ts          entry: no args → TUI, otherwise → CLI
```

- **Plugin logic is separate from plugin UI.** Every plugin, built-in or external, has a `logic` part and an optional `tui` part (§3.1). The CLI loads only logic. The TUI loads logic plus tui. A later web or other front end could reuse every plugin's logic unchanged and add its own UI part.

- **Plugins own their data.** A plugin is the only code that touches its tables.
  - **Reading across plugins** goes through the **read-only views** a plugin publishes (§3.3.3). Other plugins can select from and join those views, but never the internal tables.
  - **Writing across plugins** goes only through the **write operations** a plugin exposes (§3.3.2), so validation and business rules live in one place, whoever the caller is: another plugin, the CLI, the TUI or the assistant.
  - The kernel enforces both (§3.3.1).
- **The kernel has no domain knowledge.** It doesn't know what a project or a person is. It knows plugins, registries, record references and change sets.
- **SQLite adapter.** A small adapter selects `bun:sqlite` under Bun and `node:sqlite` under Node, and presents them to [Kysely](https://kysely.dev), a dependency-free typed SQL query builder, through its `SqliteDialect`. Only the kernel holds the database connection (§3.3.1). The database runs in WAL mode with `busy_timeout = 3000` ms, so the TUI and a CLI call can be active at the same time.
- **CLI argument parsing** uses `node:util` `parseArgs`, which works in both runtimes, so no extra dependency is needed.
- **Node build.** `scripts/build-node.mjs` already compiles `src/` to `dist-node/`. The CLI path loads only plugins' logic parts, so it doesn't import OpenTUI at all and needs no `--experimental-ffi`. Even if it did import OpenTUI, the spike showed that importing works without the flag; only creating a renderer needs it. The TUI path does. The Node entry `dist-node/bin/pm.js` uses the shebang `#!/usr/bin/env -S node --experimental-ffi`, and `package.json` `bin.ttybrain` (and its short alias `bin.tb`) points to it, so `npm link` puts `ttybrain` and `tb` on the PATH. Bun users run `bun src/bin/pm.ts` or link the same way.

### Files and configuration

| What | Default | Override |
|---|---|---|
| Data root | `~/.ttybrain` | `TTYBRAIN_HOME`; all paths below default to inside it |
| Database | `~/.ttybrain/ttybrain.db` | `TTYBRAIN_DB` env var or `--db <path>` |
| Config | `~/.ttybrain/config.json` | `TTYBRAIN_CONFIG` |
| Exports | `~/pm-exports/` | `exportDir` in config |
| External plugins | `~/.ttybrain/plugins/` | `TTYBRAIN_PLUGINS` |

The config is JSON rather than TOML because JSON parses natively in both runtimes. These are the keys and their defaults:

```json
{
  "exportDir": "~/pm-exports",
  "staleContactDays": 30,
  "assistant": { "provider": "copilot" },
  "plugins": { "disabled": [] }
}
```

`assistant.provider` can be `"copilot"` or `"none"`. `plugins.disabled` lists plugin IDs to skip; built-in plugins can be disabled too, unless another enabled plugin requires them.

## 3. Plugins

A 2026-11-13 spike verified this design under Bun and Node 26. An external plugin, built separately and loaded both from a folder and from an `npm install`, added a table, a CLI command, a screen and a tab on the project detail. Its reactive UI updated correctly in both runtimes.

### 3.1 What a plugin is

A plugin is an ESM package with two entry points. Every built-in plugin is structured the same way.

**Logic** (required, `main`). This is everything that isn't UI: migrations, published views, exposed operations, CLI commands, record types, tag types, reports and report sections (as data), assistant tools and guide sections.

```ts
// src/logic/index.ts
export default definePlugin({
  id: "contracts",                 // unique, [a-z][a-z0-9-]*; also the table prefix
  name: "Contracts",
  apiVersion: 1,                   // plugin API version it was built for
  requires: { projects: "^1" },    // plugins it needs, with version ranges; loaded first
  reads: { people: "^1" },         // optional: published views it reads; works without the plugin
  activate(ctx: PluginContext) { /* data, views, operations, commands, tools… */ },
})
```

**TUI** (optional, `ttybrain.tui` in `package.json`). This holds the terminal UI: screens, record tabs, Overview panels, list columns, field editors, global actions, status badges and quick-action menus.

```ts
// src/tui/index.tsx
export default defineTui({
  plugin: "contracts",
  activate(ui: TuiContext) { ui.screen(…); ui.recordTab("project", …); ui.overviewPanel(…) },
})
```

**Rules for the split**
- **Logic must not import UI modules.** `ttybrain plugin build` fails if the logic entry, directly or through its own files, imports `solid-js`, `@opentui/*` or `@ttybrain/api/tui`. Logic imports only `@ttybrain/api`.
- **The TUI part never touches data directly.** It uses the same `ctx.data` (its own tables and published views) and exposed operations through `ui.data`, `ui.use(...)` and `ui.call(...)`. All rules stay in logic.
- **Data-side definitions live in logic, rendering in tui.** Report sections return structured data, and the kernel renders them as Markdown, text or JSON. A `field` is declared in logic (name, type, get and set through operations); the TUI only adds the editor, or uses the default one for its type.
- **A plugin without a TUI part still works fully.** Its data shows up in the CLI, the assistant, reports, and generic record views.
- **Loading.** The CLI and any non-TUI host load only `main`. The TUI loads `main`, then `ttybrain.tui`. A TUI part that fails to load doesn't disable the logic part: the error appears in the help overlay and the plugin's data stays available.

`package.json` marks the package as a ttybrain plugin (`ttybrain.id` is required and must equal the `PluginDef` id, so a disabled plugin is known without importing it; `version` must equal `PluginDef.version`) and declares ttybrain's shared modules as **optional** peer dependencies. That way `npm install` doesn't pull in a second copy of them; the spike showed it would otherwise add about 104 packages.

```json
{
  "name": "ttybrain-plugin-contracts", "type": "module", "main": "dist/logic/index.js",
  "ttybrain": { "plugin": true, "id": "contracts", "tui": "dist/tui/index.js" },
  "peerDependencies": { "solid-js": "^1.9", "@opentui/solid": "^0.8", "@opentui/core": "^0.8", "@ttybrain/api": "^1" },
  "peerDependenciesMeta": { "solid-js": { "optional": true }, "@opentui/solid": { "optional": true }, "@opentui/core": { "optional": true }, "@ttybrain/api": { "optional": true } }
}
```

`@ttybrain/api` is ttybrain's plugin API: types, `definePlugin`, the data API types and schema builders. `@ttybrain/api/tui` adds `defineTui` and the UI building blocks (§3.4). Both are provided by the host at runtime, like Solid (§3.6).

### 3.2 Loading

1. **Built-in plugins** are packages like any other: each `src/plugins/<id>/package.json` is a manifest (source entries; the Node build writes `.js` ones to `dist-node/plugins/<id>/`), found by the same loader (`src/kernel/loader.ts`), importing only `@ttybrain/api` and `@ttybrain/api/tui`. They load first, then folders, then npm dependencies. Disabled plugins are never imported.
2. **External plugins** are found in `~/.ttybrain/plugins/` in two forms:
   - plugin folders, each with a `package.json`;
   - an npm prefix: `~/.ttybrain/plugins/package.json` whose `dependencies` are installed in `node_modules`.
   Importing an external plugin and its `activate` are each limited to 5 s. An external plugin whose id equals a built-in's, or another plugin's, fails.
3. All plugins are sorted by `requires`. A missing, disabled or wrong-version requirement, or a cycle, skips the plugin with an error message.
4. Each plugin's logic `activate(ctx)` runs, then its pending migrations, then the kernel creates its published views. In the TUI, each plugin's `tui` part is then loaded and activated, in the same order.
5. **Version check.** A plugin whose `apiVersion` is newer than the kernel's, or older than the oldest version the kernel still supports, is skipped with a message.
6. **Failure isolation.** If importing, activating or migrating a plugin fails, that plugin is marked failed and ttybrain carries on with the rest:
   - `ttybrain plugin list` and the TUI's help overlay show the error;
   - anything the plugin registered before failing is unregistered;
   - a failed migration is rolled back, because each migration runs in its own transaction.

### 3.3 What a plugin can register (the API)

`ctx` gives a plugin:

| Method | Purpose |
|---|---|
| `ctx.data` | the kernel's **data API** for this plugin (§3.3.1): a Kysely query builder scoped to the plugin's own tables. There is no database handle and no raw SQL |
| `ctx.migration(id, (schema) => …)` | an ordered migration written with the scoped Kysely **schema builder** (`schema.createTable("contract")…`). Tracked per plugin in the kernel table `kernel_plugin_migration(plugin, id, applied_at)` |
| `ctx.recordType(def)` | a record type others can reference: name, display-ID prefix (`A-`, `R-`, …, and new ones such as `C-`), `resolve(ref)`, `label(record)`, `search(text)` for autocomplete, and the screen to open |
| `ctx.publish(name, def)` | a published read-only view (§3.3.3) |
| `ctx.expose({ read, write })` | the plugin's public operations (§3.3.2). Everything not published or exposed is private |
| `ctx.use(id)` | another plugin's exposed operations. The plugin must be listed in `requires`; otherwise the call returns `undefined` for optional use |
| `ctx.command(def)` | a CLI command: thing, verb, flags (schema), `run`. It gets `--json`, `--help`, error mapping and exit codes from the kernel |
| `ctx.tool(def)` | an extra assistant tool that combines several operations. Most tools need no registration, because exposed operations become tools automatically (§3.3.2) |
| `ctx.on(event, fn)` | kernel and plugin events, e.g. `record.changed` or `inbox.captured` |

#### 3.3.1 Data access goes through the kernel

Plugins never touch the database. They describe queries with the kernel's data API, and the kernel checks, compiles and runs them. Everything lives in one database file, so a change set that spans plugins is still one atomic transaction (§3.5).

```ts
// inside the "contracts" plugin
ctx.migration("001", (schema) =>
  schema.createTable("contract")
    .addColumn("id", "integer", (c) => c.primaryKey())
    .addColumn("project_id", "integer")          // soft reference (§3.8)
    .addColumn("title", "text", (c) => c.notNull())
    .addColumn("value", "integer"))

const big = await ctx.data.selectFrom("contract")
  .select(["id", "title", "value"]).where("value", ">", 100).orderBy("value", "desc").execute()
const totals = await ctx.data.selectFrom("contract")
  .select((eb) => [eb.fn.countAll().as("n"), eb.fn.sum("value").as("total")]).executeTakeFirst()
```

- **Short table names, kernel-owned namespace.** A plugin names its tables `contract` and `party`. The kernel stores them as `<plugin>_<table>` (`contracts_contract`), and every query a plugin builds is rewritten to those names. A plugin can only address names it created in its own migrations. This applies to built-in plugins too, so §4's `project` is physically `projects_project`.
- **Layer 1: the query check.** Before a query runs, a kernel transformer walks Kysely's query tree. Every table reference, including joins, sub-queries, `insert … select`, updates, deletes and schema statements, must be one of the plugin's own tables, a **published view** written `<plugin>.<view>` (read-only, §3.3.3), or an alias of either. Column references to a published view are checked against its declared columns. Anything else is rejected with `IsolationError: table "project" is not owned by plugin "contracts"; read projects.project or use projects.<operation> instead`. Writes, updates and deletes on a published view are rejected. Index and constraint names get the same prefix.
- **Layer 2: the SQL check.** Kysely also lets you write raw `sql` fragments, and a plugin could bring its own copy of Kysely. So the kernel checks the **final compiled SQL** on that plugin's connection before running it. It runs `EXPLAIN` once per distinct statement (cached) and maps the `OpenRead`/`OpenWrite` root pages to tables through `sqlite_schema`. A statement is rejected if it touches a table that isn't one of the plugin's own, or one of the base tables behind a published view that the same query referenced (as recorded by layer 1). Schema statements are only accepted inside that plugin's migrations.
  - **Implementation note.** The set of views referenced must travel with each compiled query, not live in shared mutable state. A test version of this kernel code that kept it in shared state let a failed query's views leak into the next one.
  - **Known limit.** A raw `sql` fragment in a query that legitimately reads `people.person` could also read `people_person` directly, because both resolve to the same base table. Through the query builder this is fully enforced. For raw SQL it's a safety net.
- **Migrations.** These run only through `ctx.migration`, each in its own transaction. Afterwards the kernel compares `sqlite_schema` before and after:
  - new tables, indexes and views must carry the plugin's prefix;
  - a view may only read the plugin's own tables;
  - external plugins may not create triggers;
  - any violation rolls the migration back and marks the plugin failed.
  - Foreign keys are deferred inside a migration (`PRAGMA defer_foreign_keys`, set by the kernel), so a plugin can rebuild one of its own tables that its other tables reference (SQLite's copy, drop, create, copy back); a violation left at commit fails the commit and rolls the migration back. Don't rename the old table out of the way: a rename rewrites the references to it. Deferring does not stop `ON DELETE` actions (`CASCADE`, `SET NULL`, `SET DEFAULT`), which the drop's implicit DELETE fires; so the kernel refuses (and rolls back) a migration that drops a table while an own table referencing it with such an action still exists. Such a child is copied and dropped first, and recreated after the parent.
- **Transactions belong to the kernel.** Each call to a write operation runs in a kernel transaction, and calls nested inside one (from a change set, or a plugin calling another plugin's write) use savepoints. Plugins don't start transactions themselves. Whether this works smoothly with per-plugin Kysely instances on one connection still has to be confirmed in phase 1.
- **Kernel tables** (`kernel_plugin_migration`, `kernel_change_set`, `kernel_change_set_op`) aren't visible to plugins.
- **Verified 2026-11-13** with `kysely` 0.27 on `bun:sqlite` (Bun 1.4) and `node:sqlite` (Node 26.13):
  - select with where and order, count and sum, a join between a plugin's own tables, insert, update, and schema creation all work;
  - cross-plugin select, join, update and sub-query are rejected by layer 1;
  - a raw `sql` query on another plugin's table is rejected by layer 2.
- **Limits.** Plugins run in ttybrain's process with file access, so this catches mistakes and keeps the boundary honest. It doesn't stop deliberately malicious code (§3.7, "Trust").
- **Typing.** `@ttybrain/api` lets a plugin declare its table types once (`interface ContractsTables { contract: { id: number; title: string; … } }`) so that `ctx.data` queries are fully typed.

#### 3.3.3 Published views (cross-plugin reads)

A plugin publishes deliberate, read-only **shapes** of its data. Other plugins query them like tables, using `<plugin>.<view>`:

```ts
// in the people plugin
ctx.publish("person", {
  version: 1,
  columns: { id: "integer", handle: "text", name: "text", is_team: "boolean", is_stakeholder: "boolean",
             influence: "text", interest: "text", last_contact: "date", archived: "boolean" },
  query: (db) => db.selectFrom("person as p").select([
    "p.id", "p.handle", "p.name", "p.is_team", "p.is_stakeholder", "p.influence", "p.interest",
    (eb) => eb.selectFrom("note").whereRef("note.person_id", "=", "p.id").select(eb.fn.max("date")).as("last_contact"),
    (eb) => eb("p.archived_at", "is not", null).as("archived"),
  ]),
})

// in the projects plugin: one query for the Actions screen
ctx.data.selectFrom("action as a")
  .leftJoin("people.person as o", "o.id", "a.owner_id")
  .leftJoin("people.person as f", "f.id", "a.for_person_id")
  .select(["a.id", "a.title", "a.due_date", "o.name as owner", "f.name as for_person"])
  .where("a.status", "=", "open").orderBy("a.due_date")
```

- **Built from the plugin's own tables.** The view's query is built with the plugin's own scoped `ctx.data`, so it can only read the plugin's own tables. The kernel creates it as an SQLite view named `<plugin>__pub_<view>`. Views are definitions in code, not data, so the kernel recreates them at every startup, after migrations.
- **A view is a contract.** Its columns are declared, and checked against the actual view at startup. The owning plugin can change its internal tables freely, as long as each published view keeps its columns. Adding a column is compatible. Removing or renaming one raises the plugin's major version.
- **Dependencies.** Reading a view needs no `requires`; a plugin declares the views it uses in `reads` (with a version range). If the publishing plugin isn't loaded or has an incompatible version, its views don't exist, and a query on them fails with `ViewUnavailableError`. The calling screen or panel shows that in place, or the plugin falls back gracefully. This is what lets `people` read `projects.involvement` (for its Projects column) while `projects` requires `people`, without a cycle.
- **Read only.** The kernel rejects writes. SQLite itself also refuses them, because the views have no triggers.
- **Typing.** `@ttybrain/api` gives each published view a TypeScript type, so joins with them are typed.
- **Assistant.** Each published view is also offered to the assistant as a read tool (filter, sort, limit), unless it's marked `assistant: false`.
- **When to use what:**
  - **published views** for lists, joins, filters and counts across plugins;
  - **exposed read operations** for reads with real logic, e.g. `projectStatus`, `sinceDate`, `staleStakeholders`;
  - **exposed write operations** for every change.
- **Verified 2026-11-13** on Bun 1.4 and Node 26.13 with Kysely:
  - joining a plugin's own table with another plugin's published view works, including a computed column (`last_contact`);
  - an unpublished name, another plugin's internal table, a write to a view, and raw SQL on an internal table are all rejected.
  - Selecting a column that a view doesn't publish errors on Node. On Bun it returns the column name as a string, because Bun's SQLite treats unknown double-quoted names as text. No data leaks either way, and the layer 1 column check makes both runtimes fail the same way.

#### 3.3.2 Exposed operations

Each plugin declares its write operations, and the few read operations that carry logic. Plain cross-plugin reads use published views (§3.3.3).

```ts
ctx.expose({
  read: {
    projectStatus: { input: { project: "string", since: "date" }, output: ProjectStatusSchema, run: (i) => … },
    getContext:    { input: { project: "string" }, output: ContextSchema, run: (i) => … },
  },
  write: {
    addAction: { input: NewActionSchema, output: ActionSchema,
                 describe: (i) => `+ action "${i.title}"`, run: (i) => … },
    setHealth: { input: HealthSchema, output: HealthUpdateSchema,
                 describe: (i) => `~ ${i.code} health → ${i.health}`, run: (i) => … },
  },
})
```

- **Schemas.** Every operation has an input and an output schema, written in JSON Schema through a small builder in `@ttybrain/api`. The kernel validates the input before `run` and the output after it (output only in tests). The owning plugin's business rules run inside `run`.
- **Calls.** `ctx.use("projects").read.projectStatus({ project: "CRM", since })` and `….write.addAction({...})`. Write calls from another plugin run in the caller's current transaction, or in a new one.
- **`describe(input)`** renders a write as one line for change sets and logs. It may show a before → after diff, using the plugin's own read operations.
- **Assistant tools come from this.** Every exposed operation becomes an assistant tool automatically: reads run directly, writes go into the change set. An operation can opt out with `assistant: false`, or set its own `toolDescription`.
- **CLI commands stay separate** (`ctx.command`), because their flags and human-readable output are designed per command. A command's `run` normally just calls the plugin's own exposed operations.
- **Compatibility.** Exposed operations are a plugin's public API. Adding operations or optional input fields is compatible. Removing or changing them needs a new plugin major version, and dependants declare a version range in `requires` (e.g. `requires: { projects: "^1" }`).

### 3.4 Extension points (UI and reports)

Plugins add UI through these named extension points, and through nothing else:

| Extension point | Example |
|---|---|
| `screen` | a top-level screen in the switcher and number keys (built-ins take `1`–`6`, external ones get `7`, `8`, … in load order) |
| `recordTab` (record type, tab) | a "Contracts" tab on project detail, a "Jira" tab on a project |
| `overviewPanel` | a panel on the Overview screen, with a priority for its position |
| `reportSection` (report, section) | a section in the project prep block, the board pack or the minutes |
| `field` (record type, field) | an extra field on a record, shown in Summary or detail, forms, `show --json` and `edit --<flag>`. The plugin stores the value in its own table |
| `listColumn` (list, column) | an extra column in Projects, People or Actions |
| `tagType` | an inbox tag prefix such as `$contract`, with a resolver. `#` and `@` are taken by projects and people |
| `quickAction` (record type) | an entry in a record's action menu (`.` key), with an optional direct key, e.g. "Create Jira ticket" |
| `globalAction` | a key that works on every screen and opens an overlay or side pane: inbox capture `i`, assistant `c`. Keys are claimed at load; a conflict skips the later plugin's action with a message |
| `statusBadge` | a short live indicator in the header, e.g. `● 3 new in inbox`, `● assistant` |
| `report` | a named report, e.g. `project-status`, `board`, `minutes`, that others can add `reportSection`s to; rendered by the kernel as md, text or json. Its params become `ttybrain report` arguments and flags, so they may not be named like a global flag or `format`. An optional `prepare(params)` validates and normalises them once per run (an error there fails the command; a section's error becomes a note in the report) |
| `guideSection` | a Markdown section of the agent guide (`ttybrain guide`) |
| `assistantProvider` | an AI provider implementing `AssistantProvider` (§7), selectable in `assistant.provider` |

- **Logic or TUI.** `tagType`, `report`, `reportSection`, `guideSection`, `assistantProvider` and the data side of `field` are registered by the **logic** part. `screen`, `recordTab`, `overviewPanel`, `listColumn`, `globalAction`, `statusBadge`, `quickAction` and field editors are registered by the **tui** part.
- **Components.** UI extension points take Solid components. `@ttybrain/api/tui` gives plugins the same building blocks the built-ins use: `Panel`, `Table`, `Form`, `Field`, `KeyHints` and `useRecord`. Plugin screens therefore look and behave like the rest of ttybrain.
- **Keyboard and focus.** ttybrain owns the global keys. A plugin component receives keys only while it has focus, and declares its keys in the status bar through `KeyHints`.
- **Stability.** Every extension point is part of `apiVersion` 1. Adding an extension point or an optional field is compatible. Removing or changing one raises `apiVersion`.

### 3.5 Change sets

Every write through the assistant, and every plugin `quickAction` marked `confirm`, goes through the kernel's change set:
1. Each proposed operation is a call to an exposed **write** operation: `{ plugin, operation, input }`. Its line comes from that operation's `describe(input)`.
2. The TUI shows the list of operations.
3. The accepted operations run in **one transaction**, through the owning plugins' write operations. If any of them throws, the whole set is rolled back and the error is shown next to the failing line.
4. Applied change sets are logged in kernel tables (`kernel_change_set`, `kernel_change_set_op`) with their origin: assistant, quick action or inbox item.

### 3.6 Shared modules and the plugin build

A plugin must use **ttybrain's own** instances of `solid-js`, `solid-js/store`, `@opentui/solid`, `@opentui/core`, `@ttybrain/api` and `@ttybrain/api/tui`. Only the tui part may import the UI ones. Two Solid copies is a known cause of UIs that stop updating; the spike used one shared instance and didn't test the duplicate case.

- At startup, the kernel puts those module objects on `globalThis.__TTYBRAIN_MODULES__` (`@ttybrain/api` always; the UI ones when the TUI starts).
- `ttybrain plugin build [dir]` compiles the plugin's `src/` to `dist/` with the same Babel setup as ttybrain's Node build: `babel-preset-solid`, universal mode, `moduleName: "@opentui/solid"`. It rewrites imports of the shared modules to generated shim files in `dist/__pm/`. Each shim re-exports the host's module, and fails with a clear message if the plugin is loaded outside ttybrain.
- The output is plain ESM JavaScript, so one build runs on Bun and on Node. Plugins don't need OpenTUI's Bun-only runtime-plugin loader.
- Shims are generated from the names the plugin imports (named imports only; `import * as` fails the build). A plugin built against an older ttybrain that uses an export which has since been removed fails at load with a "rebuild the plugin" message. This is covered by failure isolation (§3.2).

### 3.7 Plugin commands

```
ttybrain plugin list                  # id, version, source (built-in/folder/npm), status (ok/failed/disabled), error
ttybrain plugin add <npm-name|path|tgz>   # runs `npm install` in ~/.ttybrain/plugins (creates its package.json if needed)
ttybrain plugin remove <id> --yes     # destructive: npm uninstall or remove the folder; tables stay unless --purge-data; a built-in is refused (disable it)
ttybrain plugin enable|disable <id>   # edits plugins.disabled in config
ttybrain plugin build [dir]           # build a plugin for development
ttybrain plugin new <id>              # scaffold a plugin folder with an example screen, tab, command and test
```

`ttybrain plugin add` needs `npm` on the PATH. Under Bun it uses `bun add --cwd ~/.ttybrain/plugins` when npm is missing.

**Trust.** Plugins run in ttybrain's process with full access to your files and data, like any npm package. ttybrain warns on the first `ttybrain plugin add` from a source that isn't built in. There's no sandbox.

### 3.8 Where the built-ins fit

The rest of this document describes the built-in plugins:
- §4 data model: tables owned by `projects`, `people`, `meetings` and `inbox`;
- §5 inbox: the `inbox` plugin;
- §6 CLI: commands registered by each plugin, plus kernel conventions;
- §7 assistant: the `assistant` plugin, whose tools come from every plugin's `ctx.tool`;
- §8 meetings: the `meetings` plugin, whose prep blocks are assembled from `reportSection`s;
- §9 TUI: kernel frame plus each plugin's screens, tabs and panels.

The full per-plugin reference (tables, exposed operations, CLI, extension points) is in [`2026-11-13-pm-plugins.md`](2026-11-13-pm-plugins.md).

**Hard and soft references.**
- `requires` is for plugins whose exposed operations a plugin can't work without.
- `reads` is for published views it uses.
- A plugin may store a **soft reference** to another plugin's record as a plain ID column. Soft references are shown by joining the other plugin's **published view**, or through `recordType` labels, never through its internal tables. If the owning plugin is disabled, they show as "unavailable" and are left untouched. This keeps the dependency graph acyclic:

| Plugin | Requires | Reads (views) | Owns (tables in §4) | Soft references |
|---|---|---|---|---|
| `people` | — | `projects.involvement`, `projects.project` | person, note, goal | note → project |
| `projects` | `people` | `people.person`, `meetings.meeting` | project, health_update, milestone, deliverable, risk, decision, action, involvement | owners, `for` and involvement → person (validated with `people.person`); action/decision → meeting |
| `meetings` | `projects`, `people` | `people.person`, `projects.project` | meeting, attendee, agenda_item | attendee → person; agenda item → project |
| `inbox` | — | — (labels through record types) | inbox_item, inbox_link | links → any record type |
| `assistant` | — | all published views, as tools | — (session state only) | — |

- `involvement` belongs to `projects`, because it depends on both a person and a project. `projects` shows a person's "Projects & roles" through a `recordTab` on the person record type. That's the kind of extension an external plugin would make.
- `inbox` resolves `#` and `@` through the `tagType`s that `projects` and `people` register. It doesn't know about either plugin.
- `assistant` collects its tools from all plugins.
- **The Overview screen belongs to the kernel.** All of its panels are `overviewPanel`s: overdue actions and the others come from `projects`, stakeholders to contact from `people`, and the inbox count from `inbox`.

## 5. Inbox and tagging

- **Syntax.** `#CODE` tags a project and `@handle` tags a person. Tags match case-insensitively. When an item is saved, resolved tags become `inbox_link` rows. An unresolved tag stays in the text and goes into `unresolved_tags`. An item with unresolved tags is still saved.
- **Capture.**
  - TUI: `i` on any screen opens the capture overlay, with autocomplete after `#` and `@`. If you're on a project or a person, their tag is pre-filled. Enter adds a new line, Ctrl+S saves (or Esc then `s`), Esc alone cancels.
  - CLI: `ttybrain inbox add "<text>"`.
- **Processing.**
  - *By an agent through the CLI.* Copilot in your editor, for example: run `ttybrain inbox list --new --json`, create records with `--from-inbox I-n`, then `ttybrain inbox done I-n --summary "…"`.
  - *Inside ttybrain.* `P` on the Inbox screen gives the new items to the assistant (§7).
  - *By hand.* `p` turns an item into an action, note, decision, risk or health update, prefilled with the text and tags.
  - `z` dismisses an item. `u` reopens a processed or dismissed item.
- **Traceability.** The kernel records provenance (§4, Inbox). The Inbox screen lists, under each processed item, the records created from it.

## 6. CLI

The pattern is `ttybrain <thing> <verb> [args] [--flags]`. The things are: `project`, `milestone`, `deliverable`, `risk`, `decision`, `action`, `person`, `note`, `goal`, `meeting`, `inbox`, `report`, `guide`. The verbs are `list`, `show`, `add`, `edit`, plus the ones that make sense for each thing: `done`, `archive`, `delete`, `close`, `dismiss`, `agenda add|move|remove`, `context`. Examples:

```
ttybrain project add CRM "CRM replatforming" --effort 220
ttybrain project edit CRM --health amber --health-comment "Design slipping 2 weeks"   # creates a health_update
ttybrain project edit CRM --code CRM2027   # renames; links follow (by id), free text that says #CRM is not rewritten
ttybrain project context CRM [--set-file ctx.md | --stdin | --clear]
ttybrain action add "Send roadmap" --project CRM --for peter --due fri
ttybrain action list --open --overdue
ttybrain action list --owner anna --open
ttybrain risk add CRM "Vendor delay" --type risk --severity high --owner bob
ttybrain note add peter --interaction "Worried about budget" --project CRM
ttybrain meeting add "Steering committee Q4" --date 2026-12-04 --kind steering --attendees peter,marie --projects CRM,ERP
ttybrain meeting agenda M-4 add "Budget" --project CRM --ask "Release contingency"
ttybrain report board M-4 --format md > board.md
ttybrain guide                       # prints the usage guide for agents
```

**Rules**

- **JSON.** `--json` works on every command. `list` returns an array. `show`, `add` and `edit` return the full record, including its display ID. Errors return `{"error":{"code","message","hint"}}`.
- **No prompts.** Commands never ask for input. `delete` requires `--yes`.
- **Exit codes.** `0` OK, `1` validation error, `2` not found, `3` conflict or locked database. Messages say how to fix the problem, e.g. `unknown person "ana" — did you mean "anna"?`.
- **Dates.** Inputs accept `YYYY-MM-DD`, `today`, `tomorrow`, `+Nd`, `+Nw`, and weekday names (`mon` to `sun`, meaning the next such day after today). Output is always ISO.
- **References.** A person can be given as a handle, a project as a code or an ID, and any record as its display ID or a bare number.
- **Help.** `ttybrain help` and `ttybrain <thing> --help` list every flag.
- **Agent guide.** `ttybrain guide` prints a Markdown guide, made by the kernel from every plugin's `guideSection` in dependency order. It covers what ttybrain is, the most useful commands, the inbox-processing rules (concern → stakeholder note, "X will do Y" → action, "decided" → decision, "finished" → deliverable status, health signals → health update), and the rule to ask the user when something is ambiguous instead of guessing. `ttybrain guide --write <path>` writes the guide to a file, for example the user's Copilot instructions file.

## 7. Assistant (pluggable; GitHub Copilot SDK first)

```
src/plugins/assistant/logic/session.ts             chat loop and context; provider-independent
src/plugins/assistant/logic/providers/copilot.ts   adapter over @github/copilot-sdk
src/plugins/assistant/tui/pane.tsx                 chat pane and change-set review UI
```

The tools aren't defined here. They're generated from every plugin's exposed operations (§3.3.2), plus any extra `ctx.tool`s, so an external plugin's data is automatically available to the assistant, within what that plugin exposes. Change sets are a kernel service (§3.5).

Providers are pluggable in two ways. Built-in providers live in `providers/`. External plugins can add one through the `assistantProvider` extension point (§3.4).

```ts
interface AssistantProvider {
  id: string
  checkAuth(): Promise<{ ok: true } | { ok: false; howToFix: string }>
  startSession(opts: { instructions: string; tools: ToolDef[] }): Promise<ProviderSession>
}
interface ProviderSession {
  send(message: string, context: Context): AsyncIterable<AssistantEvent> // text | toolCall | done | error
  cancel(): void
  close(): Promise<void>
}
```

- **Read tools** run straight away. They're the exposed read operations (project status, reports, context) and one query tool per published view (filter, sort, limit).
- **Write tools** are the exposed write operations, and they don't write directly. They append to a **pending change set**. ttybrain shows each change (`+ action …`, `~ milestone due 26 Nov → 10 Dec`). You accept all with `y`, step through them with `Enter`, or reject with `n`. Accepted changes are applied in one transaction through the owning plugins' services (§3.5).
- **Context.** Each message carries the current screen and the selected record's key fields.
- **Instructions.** The session's instructions are the same text as `ttybrain guide`.
- **TUI pane.** `c` opens or focuses a chat pane on the right. While the pane is focused, Esc returns focus to the main area. The pane can be zoomed to full width (`Z`) or hidden (`C`); hiding keeps the session. While a session is running, the header shows `● assistant`.
- **Inbox processing in ttybrain.** `P` processes new inbox items one at a time: one change set per item, and once accepted the item is marked processed with a summary.
- **Loading.** The provider is loaded with a dynamic import only when the pane opens. `@github/copilot-sdk` is an `optionalDependency`. If it's missing, signed out or not allowed, the pane shows the `howToFix` text and the rest of ttybrain is unaffected. `assistant.provider = "none"` hides the pane.
- **Authentication (Copilot).** It uses the user's own Copilot subscription, through the stored login of the bundled Copilot CLI, or `GITHUB_TOKEN` / a configured token. The organisation's Copilot policy must allow CLI usage.
- **Risk.** The SDK is in technical preview and targets Node. The assistant phase therefore starts with a spike (§13). If the SDK doesn't run under Bun, the pane is Node-only and shows "the assistant needs Node" under Bun.

## 8. Meetings and reports

- **Creating a meeting** with `--projects` (or picking projects in the TUI) adds an agenda item per project, "<name> status", with an empty `ask`.
- **The "since" date** for a project in a meeting is the first of these that exists:
  1. the meeting's `since_date`;
  2. the date of the most recent earlier *held* meeting that had an agenda item for that project;
  3. the meeting date minus 30 days.
- **The prep block** for a project is generated on demand and never stored. It contains, in this order:
  1. current health, with comment and date, and a warning if the last health update is older than "since";
  2. milestones completed since "since", plus open milestones due within 60 days after the meeting date, with late ones marked;
  3. deliverables that changed status since "since", or are due within 30 days;
  4. open risks and issues, high severity first;
  5. decisions since "since";
  6. overdue actions, plus open actions linked to the previous meeting;
  7. the agenda item's `ask`.
- **During the meeting.** The Notes tab holds the meeting notes. `a` adds an action and `D` a decision, both linked to the meeting and to the selected agenda item's project.
- **Closing.** `ttybrain meeting close M-4` (TUI: `x`) sets the status to held and lists what was logged.
- **Reports.** Each report is a pure function of the data plus today's date:

| Command | Contents |
|---|---|
| `ttybrain report status <project>` | the prep block, with "since" = 30 days ago |
| `ttybrain report board <meeting>` | title, date, attendees, agenda with asks, then one prep block per covered project |
| `ttybrain report minutes <meeting>` | attendees, notes, decisions and actions linked to the meeting |
| `ttybrain report overview` | the Overview screen as text |

- **Formats.** `--format md` (default), `text` or `json`.
- **TUI export.** The Export tab previews the Markdown: the board pack while the meeting is planned, the minutes once it is held or cancelled, and `m` switches between them. `w` writes `<exportDir>/<date>-<slug>.md` (`<date>-<slug>-minutes.md` for the minutes) and shows the path; the slug is the title lowercased, other characters collapsed to `-`, leading and trailing `-` trimmed, cut at 40 characters, `meeting` when nothing is left, and a second export overwrites the file. `y` copies the Markdown to the clipboard through OSC 52 and says so when the terminal refuses (the web terminal ignores OSC 52 for now).
- **Board pack as built.** `ttybrain report board <meeting>` is attendees, the agenda with asks, then, per agenda project, the `project-status` report (run through `ctx.reports.run`, with `since` from `sinceDate`, `reference` = the meeting date and `previous-meeting` = the previous held meeting that covered the project) under a group heading `CODE Name · since DATE`, followed by that project's asks. `ttybrain report minutes <meeting>` is attendees, notes, and the decisions and actions linked to the meeting. Row marks (icon and tone) make the Prep tab and the Markdown readable at a glance.

Validation errors come from the owning plugin's service and show next to the field. Keys: Enter is always "new line" (a newline in a multi-line field, nothing in a one-line field); Tab / Shift+Tab change field; Ctrl+S saves and closes (or Esc then `s`); Esc alone cancels.

**Long text.** Context, notes and meeting notes are edited in a **built-in editor**: an OpenTUI textarea in a full-screen overlay, `Ctrl+S` or `Esc` then `s` to save, `Esc` then `d` to discard. It works the same locally and in the container. In local mode, `E` opens `$EDITOR` instead: the renderer is suspended, the editor runs on a temporary file, and the renderer resumes. The exact suspend API in OpenTUI still has to be confirmed in phase 2. Both are offered because a container has no `$EDITOR` (§11.2).

**Drafts.** Forms, quick capture and the built-in editor (the project Context) keep a **draft** of what was typed but not saved, so a cancel, a quit or a crash loses nothing. A draft is a JSON file in `TTYBRAIN_HOME/drafts/` (one per form and record, e.g. the edit form of `#P1`, the "new project" form, a form opened from inbox item `I-3`, quick capture, one project's Context), not in the database: typing takes no write lock, does not trigger live refresh and leaves no history. It is written 1 s after the last change, and at once on Esc and when ttybrain quits. A save deletes it, and so does the editor's confirmed discard (Esc d, then `y`); Esc cancels a form or quick capture as before but keeps it and says `draft kept`. Reopening the same thing while a draft differs from what is saved first shows `Unsaved draft from HH:MM · r restore · x discard` (with the date when it is not from today), before any typing: `r` fills in the draft, `x` deletes it and starts from the saved values, Esc closes without touching it. A draft equal to the saved values is deleted silently, and drafts older than 30 days are deleted when the TUI starts.

**Live refresh.** About once a second, `PRAGMA data_version` is checked. When it changes, the current screen's data is reloaded and the selection is kept where possible.

## 10. Errors and data safety

- **Typed errors.** The kernel defines, and plugins throw, `ValidationError` (with a field), `NotFoundError` (with suggestions) and `ConflictError`. The CLI maps them to exit codes. The TUI shows them inline, or as a status-bar message for 5 seconds. A failure in a screen never crashes the app. The status bar shows the message and the screen keeps its last data.
- **First run.** The database directory and file are created. Migrations run per plugin, each in its own transaction. Before applying a migration to an existing database, the file is copied to `ttybrain.db.bak-v<from>`.
- **Locked database.** `busy_timeout` handles short locks. Longer ones give exit code `3` in the CLI and a "database busy, retrying" message in the TUI.
- **Plugin failures** are isolated (§3.2): a broken plugin is skipped and reported, and ttybrain keeps running. An exception thrown by a plugin's screen, tab or panel is caught by an error boundary around that component, which shows the error in place.
- **Assistant failures** (signed out, network, SDK errors) show only in the assistant pane.

## 11. Deployment: local and container

ttybrain supports two deployment targets with the same code. In both, it stays a **single-user** application.

### 11.1 Local

`ttybrain` runs in your own terminal on Bun or Node 26.4+, with data in `~/.ttybrain`. This is everything described so far.

### 11.2 Container with a web terminal

**Setup.** One isolated container per user. The TUI is reached from a browser through a web terminal.

```
browser ──https──▶ auth proxy (SSO/login) ──▶ container (one per user)
                                                ├─ web terminal (e.g. ttyd; xterm.js in the browser)
                                                │    └─ runs `ttybrain` directly, with no shell
                                                ├─ Node 26 or Bun, ttybrain, npm (for plugins)
                                                └─ volume mounted at TTYBRAIN_HOME: ttybrain.db, config, plugins, exports, assistant login
```

**What ttybrain provides for this.** `TTYBRAIN_MODE=container` switches on the defaults below.

1. **One data root.** `TTYBRAIN_HOME`, default `~/.ttybrain`, contains everything persistent: the database, config, plugins, exports and assistant credentials. Every path can also be set by environment variable (`TTYBRAIN_DB`, `TTYBRAIN_CONFIG`, `TTYBRAIN_PLUGINS`, `TTYBRAIN_EXPORTS`), and config values can be overridden with `TTYBRAIN_CONFIG_JSON`. Nothing persistent is written outside `TTYBRAIN_HOME`.
2. **Clean shutdown on disconnect.** Closing the browser tab sends `SIGHUP`; `SIGTERM` comes from the container runtime. On either, ttybrain finishes or rolls back the current transaction, restores the terminal and exits with code 0. WAL mode keeps the database consistent even after a hard kill.
3. **Several sessions at once.** Two browser tabs mean two ttybrain processes on one database. This is supported through WAL, `busy_timeout` and live refresh, and covered by a test.
4. **No way out to a shell.**
   - The web terminal starts `ttybrain` as its command, and quitting ttybrain ends the session.
   - In container mode ttybrain never starts other programs: `$EDITOR` is ignored, and `ttybrain plugin add` only accepts sources from `plugins.allow` in config. There's no `!`-style command execution anywhere.
   - `Ctrl+Z` suspend is disabled.
5. **Built-in editor.** Project context, meeting notes and person notes are edited in OpenTUI's own textarea, with Markdown preview in the Context tab. This is the default everywhere; `$EDITOR` is an option only in local mode.
6. **Getting output out of the container.**
   - `y` copies to the clipboard through **OSC 52**, which the web terminal must allow.
   - Optionally, ttybrain serves a small **read-only download endpoint** for the exports folder: `TTYBRAIN_EXPORT_HTTP=:8081`, a separate port, with no directory listing beyond the exports folder. The auth proxy protects it like the terminal, and the Export tab shows the download link.
7. **Assistant sign-in.** The Copilot provider signs in once with GitHub's device-code flow, shown inside the pane, and stores the result under `TTYBRAIN_HOME`. Alternatively it uses a `GITHUB_TOKEN` passed in as a container secret. In this setup Copilot in your own editor can't reach the container's CLI, so the in-app assistant is the main Copilot route.
8. **Health check.** `ttybrain doctor` exits 0 when the database opens, migrations are current and every plugin loads. It prints problems otherwise. Usable as the container's health check.

**Image.** A `Dockerfile` in the repository builds a small image:
- Node 26, or Bun, chosen in phase 2 based on the spike;
- ttybrain installed globally;
- ttyd as the web terminal;
- a non-root user;
- `TTYBRAIN_MODE=container`;
- the entrypoint `ttyd --writable … ttybrain`.

**Out of ttybrain's scope:** the auth proxy, SSO, TLS, provisioning a container per user, backups of the volume, and resource limits. ttybrain documents what it expects from them.

**Risks, checked by a feasibility spike in phase 2.** The TUI's primary target is the user's own terminal; the container is phase 6. The spike runs early in phase 2 but doesn't block the TUI work: it only feeds key and UI choices (for example avoiding keys a browser takes), so the TUI stays usable in a web terminal later.
- **OpenTUI in xterm.js**: colours, mouse, resize, and which keyboard protocol OpenTUI negotiates; and whether `Shift+Enter`, `Esc` and arrow keys arrive correctly.
- **Browser key capture**: `Ctrl+W`, `Ctrl+T`, `Ctrl+N` and `Ctrl+C` behave differently in a browser. ttybrain's own keys must not depend on combinations a browser takes. `Ctrl+C` is never the only way to cancel, because `Esc` always works.
- **OSC 52 clipboard** through ttyd and xterm.js.
- **Responsiveness**: key-to-screen latency over the websocket, and a full redraw on a 120×40 terminal.
- **Outcome**: a recommended web terminal and its settings, or a list of key and UI changes ttybrain must make.

## 12. Testing

- **Kernel**: plugin loading order, `requires` and cycles, version checks, failure isolation, migrations per plugin, change sets (including rollback when one operation fails), and record references.
- **Isolation**: on both runtimes, queries touching another plugin's table are rejected by layer 1 (joins, sub-queries, updates, aliases) and layer 2 (raw `sql`, a plugin-bundled Kysely). Published views can be read and joined but not written. Unpublished names and undeclared columns are rejected. A missing publisher gives `ViewUnavailableError`. The views used by a failed query must not leak into the next query. Migrations that create objects without the plugin's prefix, or triggers, are rolled back.
- **Built-in plugins**: `bun test` against a temporary database file per test, with an injectable "today". This covers queries, the "since" logic, prep blocks and reports.
- **CLI**: in-process runs that check stdout, JSON shape and exit codes.
- **TUI**: `testRender` frame tests per screen, plus the key flows: capture, create and edit, filter, accepting a change set.
- **Assistant**: a scripted fake provider that drives the session, the tools and the change sets. The Copilot provider gets a manual smoke checklist.
- **External plugins**: a fixture plugin in `test/fixtures/` is built with `ttybrain plugin build`, loaded once from a folder and once from an `npm install` of its packed tarball, and exercised through a CLI command, a screen, a `recordTab` and a migration. This repeats the spike as a permanent test.
- **Logic/UI split**: the CLI test suite runs with the UI modules made unloadable, which proves the CLI path never imports them. `ttybrain plugin build` rejects a fixture whose logic imports `@opentui/solid`.
- **Container mode**: a pseudo-terminal test sends `SIGHUP` in the middle of a write and checks the database and exit code. Two concurrent ttybrain processes edit the same data. Shell escapes are refused, and the download endpoint serves only the exports folder.
- **Node**: a smoke test that builds `dist-node/` and runs a few CLI commands plus the external-plugin test under Node 26.
- **CI**: add a job to `.gitlab-ci.yml` that runs type-checking, `bun test` and the Node smoke test, next to the existing SAST.

## 13. Phases

Each phase gets its own implementation plan.

1. **Kernel and CLI, with the `people`, `projects` and `inbox` plugins (logic parts only).** `TTYBRAIN_HOME` and environment configuration, clean shutdown on `SIGHUP`/`SIGTERM`, the plugin host and registries (built-in loading only, logic/tui entry points), SQLite adapter, the Kysely-based `ctx.data` with both isolation layers and kernel-managed transactions (confirm savepoints across plugin instances first), `ctx.publish` (published views) and `ctx.expose`/`ctx.use`, per-plugin migrations, change sets, record types, date parsing, the CLI dispatcher and conventions; the three plugins' tables, services, commands, `report status|overview`, and `ttybrain guide`. After this phase Copilot in the editor can already use ttybrain.
2. **TUI kernel and the projects UI.** It targets the user's own terminal. It starts with the I4 lock fix (read-only commands must not take the write lock) and runs a **web-terminal feasibility spike** (§11.2) early, without blocking the rest. Then: Frame and switcher, forms, live refresh, error boundaries, the extension points `screen`, `recordTab`, `overviewPanel`, `listColumn` and `field`, loading plugins' `tui` parts, the `@ttybrain/api/tui` building blocks, the built-in long-text editor; Overview, Projects and project detail (including Context), Actions, quick capture, and Inbox.
3. **People UI.** The People screen, notes, goals, the stakeholder fields and sorting, and the "Projects & roles" `recordTab`.
4. **Meetings plugin.** Agenda, prep blocks assembled from `reportSection`s, notes, close, `report board|minutes`, and export.
5. **External plugins.** Loading from `~/.ttybrain/plugins` (folders and npm prefix), version checks, failure isolation for external code, shared-module shims, `ttybrain plugin build|add|remove|list|enable|disable|new`, the `tagType` and `quickAction` extension points, and the fixture-plugin test on both runtimes.
6. **Container deployment.** `TTYBRAIN_MODE=container` behaviour (§11.2), the built-in editor as the default, the OSC 52 copy and download endpoint, `ttybrain doctor`, the `Dockerfile` with ttyd, and the container-mode tests. Items that phases 1–5 depend on, such as `TTYBRAIN_HOME` and signal handling, are built in those phases already.
7. **Assistant plugin.** First a spike: Copilot SDK sign-in with the user's work account, including the device-code flow inside a container, and running under Bun and Node. Then the provider interface, tools, change sets, the Copilot provider, the chat pane, and inbox processing inside ttybrain.

## 14. Out of scope

- multiple users, sharing, sync or a server;
- importing from Excel or other tools;
- time tracking and per-person allocation (effort is one estimate per project);
- approval or sign-off of deliverables;
- a registry of recurring meetings;
- Word or PowerPoint export (Markdown only);
- the MCP integration that will fill project context (only the field and its CLI are in scope);
- assistant providers other than Copilot (only the interface is in scope);
- a plugin marketplace or registry beyond npm itself, plugin sandboxing, and plugin settings screens;
- any specific external plugin (Jira, calendar, budgets…); only the API and the fixture plugin are in scope;
- running ttybrain as a multi-user service. Each container serves one user, and the auth proxy, provisioning, TLS and volume backups belong to the hosting setup;
- web UIs other than the web terminal. The logic/UI split keeps this possible later.
