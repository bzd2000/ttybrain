# pm: personal project-portfolio tool — design

Date: 2026-11-13 · Status: draft for review (rev. 5: plugin architecture, kernel-mediated data access, published views)

Screen mockups: [`2026-11-13-pm-screens.html`](2026-11-13-pm-screens.html) (published at https://claude.ai/artifact/AtQuEpRLAjmtxaKEHXU4N2). Per-plugin data, operations and UI contributions: [`2026-11-13-pm-plugins.md`](2026-11-13-pm-plugins.md). Where the mockups and this document disagree, this document wins. Known differences: the home screen is called **Overview** (mockups say "Attention") and the project's first tab is called **Summary** (mockups say "Overview").

## 1. Purpose

A personal terminal tool for someone responsible for a portfolio of projects. It helps them:

1. manage and follow up the projects under their responsibility;
2. manage and follow up the team working on those projects;
3. manage and follow up the stakeholders of those projects;
4. prepare meetings and boards about those projects.

It also lets GitHub Copilot read and update the data, and it has an inbox for quick capture that Copilot can process.

**Users and scale.** One user. Data stays on that person's machine. There are no accounts, no sharing and no sync. Expected size: 20–30 active projects, about 20 active stakeholders, a team of about 10, and 5–10 board meetings. Nothing needs paging or indexes beyond the basics.

**Success looks like:**
- one screen that shows what needs attention today;
- capturing a thought takes about five seconds from any screen;
- a board pack comes from the data instead of being written by hand;
- Copilot can do routine updates safely.

**Starting point.** The repository already holds an OpenTUI + Solid starter that runs on Bun and on Node 26.4+ (see `CLAUDE.md`). Both runtimes must keep working. Nothing has to be imported: you start with an empty database.

## 2. Architecture

pm is a small **kernel** plus **plugins**. Every feature area, the built-in ones included, is a plugin written against the same plugin API (§3). The kernel provides the plumbing and the three front ends.

```
src/kernel/            plugin host, registries, SQLite adapter, migrations runner, config,
                       record references, date parsing, typed errors, change sets
src/kernel/cli/        `pm <thing> <verb>`: dispatches to commands registered by plugins
src/kernel/tui/        frame, screen switcher, forms, live refresh; renders screens, tabs
                       and panels registered by plugins
src/plugins/projects/  built-in: projects, health, milestones, deliverables, risks, decisions, actions
src/plugins/people/    built-in: people (team and stakeholders), involvement, notes, goals
src/plugins/meetings/  built-in: meetings, agenda, prep, reports, export
src/plugins/inbox/     built-in: inbox, tags, processing
src/plugins/assistant/ built-in: chat session, change-set approval, providers/ (copilot first)
src/bin/pm.ts          entry: no args → TUI, otherwise → CLI
```

- **Plugins own their data.** A plugin is the only code that touches its tables.
  - **Reading across plugins** goes through the **read-only views** a plugin publishes (§3.3.3). Other plugins can select from and join those views, but never the internal tables.
  - **Writing across plugins** goes only through the **write operations** a plugin exposes (§3.3.2), so validation and business rules live in one place, whoever the caller is: another plugin, the CLI, the TUI or the assistant.
  - The kernel enforces both (§3.3.1).
- **The kernel has no domain knowledge.** It doesn't know what a project or a person is. It knows plugins, registries, record references and change sets.
- **SQLite adapter.** A small adapter selects `bun:sqlite` under Bun and `node:sqlite` under Node, and presents them to [Kysely](https://kysely.dev), a dependency-free typed SQL query builder, through its `SqliteDialect`. Only the kernel holds the database connection (§3.3.1). The database runs in WAL mode with `busy_timeout = 3000` ms, so the TUI and a CLI call can be active at the same time.
- **CLI argument parsing** uses `node:util` `parseArgs`, which works in both runtimes, so no extra dependency is needed.
- **Node build.** `scripts/build-node.mjs` already compiles `src/` to `dist-node/`. The CLI path imports OpenTUI modules (they're handed to plugins, §3.6) but never creates a renderer, so the CLI needs no `--experimental-ffi`. The spike confirmed this. The TUI path does. The Node entry `dist-node/bin/pm.js` uses the shebang `#!/usr/bin/env -S node --experimental-ffi`, and `package.json` `bin.pm` points to it, so `npm link` puts `pm` on the PATH. Bun users run `bun src/bin/pm.ts` or link the same way.

### Files and configuration

| What | Default | Override |
|---|---|---|
| Database | `~/.pm/pm.db` | `PM_DB` env var or `--db <path>` |
| Config | `~/.pm/config.json` | `PM_CONFIG` |
| Exports | `~/pm-exports/` | `exportDir` in config |
| External plugins | `~/.pm/plugins/` | `PM_PLUGINS` |

The config is JSON rather than TOML because JSON parses natively in both runtimes. These are the keys and their defaults:

```json
{
  "exportDir": "~/pm-exports",
  "staleContactDays": 30,
  "assistant": { "provider": "copilot" },
  "plugins": { "disabled": [] }
}
```

`assistant.provider` can be `"copilot"` or `"none"`. `plugins.disabled` lists plugin IDs to skip; built-in plugins can be disabled too, unless another enabled plugin requires them.

## 3. Plugins

A 2026-11-13 spike verified this design under Bun and Node 26. An external plugin, built separately and loaded both from a folder and from an `npm install`, added a table, a CLI command, a screen and a tab on the project detail. Its reactive UI updated correctly in both runtimes.

### 3.1 What a plugin is

A plugin is an ESM package whose default export is:

```ts
export default definePlugin({
  id: "contracts",                 // unique, [a-z][a-z0-9-]*; also the table prefix
  name: "Contracts",
  apiVersion: 1,                   // plugin API version it was built for
  requires: { projects: "^1" },    // plugins it needs, with version ranges; loaded first
  reads: { people: "^1" },         // optional: published views it reads; works without the plugin
  activate(ctx: PluginContext) { /* register everything here */ },
})
```

`package.json` marks the package as a pm plugin and declares pm's shared modules as **optional** peer dependencies. That way `npm install` doesn't pull in a second copy of them; the spike showed it would otherwise add about 104 packages.

```json
{
  "name": "pm-plugin-contracts", "type": "module", "main": "dist/index.js",
  "pm": { "plugin": true },
  "peerDependencies": { "solid-js": "^1.9", "@opentui/solid": "^0.8", "@opentui/core": "^0.8", "@pm/api": "^1" },
  "peerDependenciesMeta": { "solid-js": { "optional": true }, "@opentui/solid": { "optional": true }, "@opentui/core": { "optional": true }, "@pm/api": { "optional": true } }
}
```

`@pm/api` is pm's plugin API: types plus `definePlugin` and the UI building blocks (§3.4). It's provided by the host at runtime, like Solid (§3.6).

### 3.2 Loading

1. **Built-in plugins** are imported statically by the kernel.
2. **External plugins** are found in `~/.pm/plugins/` in two forms:
   - plugin folders, each with a `package.json`;
   - an npm prefix: `~/.pm/plugins/package.json` whose `dependencies` are installed in `node_modules`.
3. All plugins are sorted by `requires`. A missing, disabled or wrong-version requirement, or a cycle, skips the plugin with an error message.
4. Each plugin's `activate(ctx)` runs, then its pending migrations.
5. **Version check.** A plugin whose `apiVersion` is newer than the kernel's, or older than the oldest version the kernel still supports, is skipped with a message.
6. **Failure isolation.** If importing, activating or migrating a plugin fails, that plugin is marked failed and pm carries on with the rest:
   - `pm plugin list` and the TUI's help overlay show the error;
   - anything the plugin registered before failing is unregistered;
   - a failed migration is rolled back, because each migration runs in its own transaction.

### 3.3 What a plugin can register (the API)

`ctx` gives a plugin:

| Method | Purpose |
|---|---|
| `ctx.data` | the kernel's **data API** for this plugin (§3.3.1): a Kysely query builder scoped to the plugin's own tables. There is no database handle and no raw SQL |
| `ctx.migration(id, (schema) => …)` | an ordered migration written with the scoped Kysely **schema builder** (`schema.createTable("contract")…`). Tracked per plugin in the kernel table `kernel_plugin_migration(plugin, id, applied_at)` |
| `ctx.recordType(def)` | a record type others can reference: name, display-ID prefix (`A-`, `R-`, …, and new ones such as `C-`), `resolve(ref)`, `label(record)`, `search(text)` for autocomplete, and the screen to open |
| `ctx.publish(name, def)` | a published read-only view (§3.3.3) |
| `ctx.expose({ read, write })` | the plugin's public operations (§3.3.2). Everything not published or exposed is private |
| `ctx.use(id)` | another plugin's exposed operations. The plugin must be listed in `requires`; otherwise the call returns `undefined` for optional use |
| `ctx.command(def)` | a CLI command: thing, verb, flags (schema), `run`. It gets `--json`, `--help`, error mapping and exit codes from the kernel |
| `ctx.tool(def)` | an extra assistant tool that combines several operations. Most tools need no registration, because exposed operations become tools automatically (§3.3.2) |
| `ctx.on(event, fn)` | kernel and plugin events, e.g. `record.changed` or `inbox.captured` |

#### 3.3.1 Data access goes through the kernel

Plugins never touch the database. They describe queries with the kernel's data API, and the kernel checks, compiles and runs them. Everything lives in one database file, so a change set that spans plugins is still one atomic transaction (§3.5).

```ts
// inside the "contracts" plugin
ctx.migration("001", (schema) =>
  schema.createTable("contract")
    .addColumn("id", "integer", (c) => c.primaryKey())
    .addColumn("project_id", "integer")          // soft reference (§3.8)
    .addColumn("title", "text", (c) => c.notNull())
    .addColumn("value", "integer"))

const big = await ctx.data.selectFrom("contract")
  .select(["id", "title", "value"]).where("value", ">", 100).orderBy("value", "desc").execute()
const totals = await ctx.data.selectFrom("contract")
  .select((eb) => [eb.fn.countAll().as("n"), eb.fn.sum("value").as("total")]).executeTakeFirst()
```

- **Short table names, kernel-owned namespace.** A plugin names its tables `contract` and `party`. The kernel stores them as `<plugin>_<table>` (`contracts_contract`), and every query a plugin builds is rewritten to those names. A plugin can only address names it created in its own migrations. This applies to built-in plugins too, so §4's `project` is physically `projects_project`.
- **Layer 1: the query check.** Before a query runs, a kernel transformer walks Kysely's query tree. Every table reference, including joins, sub-queries, `insert … select`, updates, deletes and schema statements, must be one of the plugin's own tables, a **published view** written `<plugin>.<view>` (read-only, §3.3.3), or an alias of either. Column references to a published view are checked against its declared columns. Anything else is rejected with `IsolationError: table "project" is not owned by plugin "contracts"; read projects.project or use projects.<operation> instead`. Writes, updates and deletes on a published view are rejected. Index and constraint names get the same prefix.
- **Layer 2: the SQL check.** Kysely also lets you write raw `sql` fragments, and a plugin could bring its own copy of Kysely. So the kernel checks the **final compiled SQL** on that plugin's connection before running it. It runs `EXPLAIN` once per distinct statement (cached) and maps the `OpenRead`/`OpenWrite` root pages to tables through `sqlite_schema`. A statement is rejected if it touches a table that isn't one of the plugin's own, or one of the base tables behind a published view that the same query referenced (as recorded by layer 1). Schema statements are only accepted inside that plugin's migrations.
  - **Implementation note.** The set of views referenced must travel with each compiled query, not live in shared mutable state. A test version of this kernel code that kept it in shared state let a failed query's views leak into the next one.
  - **Known limit.** A raw `sql` fragment in a query that legitimately reads `people.person` could also read `people_person` directly, because both resolve to the same base table. Through the query builder this is fully enforced. For raw SQL it's a safety net.
- **Migrations.** These run only through `ctx.migration`, each in its own transaction. Afterwards the kernel compares `sqlite_schema` before and after:
  - new tables, indexes and views must carry the plugin's prefix;
  - a view may only read the plugin's own tables;
  - external plugins may not create triggers;
  - any violation rolls the migration back and marks the plugin failed.
- **Transactions belong to the kernel.** Each call to a write operation runs in a kernel transaction, and calls nested inside one (from a change set, or a plugin calling another plugin's write) use savepoints. Plugins don't start transactions themselves. Whether this works smoothly with per-plugin Kysely instances on one connection still has to be confirmed in phase 1.
- **Kernel tables** (`kernel_plugin_migration`, `kernel_change_set`, `kernel_change_set_op`) aren't visible to plugins.
- **Verified 2026-11-13** with `kysely` 0.27 on `bun:sqlite` (Bun 1.4) and `node:sqlite` (Node 26.13):
  - select with where and order, count and sum, a join between a plugin's own tables, insert, update, and schema creation all work;
  - cross-plugin select, join, update and sub-query are rejected by layer 1;
  - a raw `sql` query on another plugin's table is rejected by layer 2.
- **Limits.** Plugins run in pm's process with file access, so this catches mistakes and keeps the boundary honest. It doesn't stop deliberately malicious code (§3.7, "Trust").
- **Typing.** `@pm/api` lets a plugin declare its table types once (`interface ContractsTables { contract: { id: number; title: string; … } }`) so that `ctx.data` queries are fully typed.

#### 3.3.3 Published views (cross-plugin reads)

A plugin publishes deliberate, read-only **shapes** of its data. Other plugins query them like tables, using `<plugin>.<view>`:

```ts
// in the people plugin
ctx.publish("person", {
  version: 1,
  columns: { id: "integer", handle: "text", name: "text", is_team: "boolean", is_stakeholder: "boolean",
             influence: "text", interest: "text", last_contact: "date", archived: "boolean" },
  query: (db) => db.selectFrom("person as p").select([
    "p.id", "p.handle", "p.name", "p.is_team", "p.is_stakeholder", "p.influence", "p.interest",
    (eb) => eb.selectFrom("note").whereRef("note.person_id", "=", "p.id").select(eb.fn.max("date")).as("last_contact"),
    (eb) => eb("p.archived_at", "is not", null).as("archived"),
  ]),
})

// in the projects plugin: one query for the Actions screen
ctx.data.selectFrom("action as a")
  .leftJoin("people.person as o", "o.id", "a.owner_id")
  .leftJoin("people.person as f", "f.id", "a.for_person_id")
  .select(["a.id", "a.title", "a.due_date", "o.name as owner", "f.name as for_person"])
  .where("a.status", "=", "open").orderBy("a.due_date")
```

- **Built from the plugin's own tables.** The view's query is built with the plugin's own scoped `ctx.data`, so it can only read the plugin's own tables. The kernel creates it as an SQLite view named `<plugin>__pub_<view>`. Views are definitions in code, not data, so the kernel recreates them at every startup, after migrations.
- **A view is a contract.** Its columns are declared, and checked against the actual view at startup. The owning plugin can change its internal tables freely, as long as each published view keeps its columns. Adding a column is compatible. Removing or renaming one raises the plugin's major version.
- **Dependencies.** Reading a view needs no `requires`; a plugin declares the views it uses in `reads` (with a version range). If the publishing plugin isn't loaded or has an incompatible version, its views don't exist, and a query on them fails with `ViewUnavailableError`. The calling screen or panel shows that in place, or the plugin falls back gracefully. This is what lets `people` read `projects.involvement` (for its Projects column) while `projects` requires `people`, without a cycle.
- **Read only.** The kernel rejects writes. SQLite itself also refuses them, because the views have no triggers.
- **Typing.** `@pm/api` gives each published view a TypeScript type, so joins with them are typed.
- **Assistant.** Each published view is also offered to the assistant as a read tool (filter, sort, limit), unless it's marked `assistant: false`.
- **When to use what:**
  - **published views** for lists, joins, filters and counts across plugins;
  - **exposed read operations** for reads with real logic, e.g. `projectStatus`, `sinceDate`, `staleStakeholders`;
  - **exposed write operations** for every change.
- **Verified 2026-11-13** on Bun 1.4 and Node 26.13 with Kysely:
  - joining a plugin's own table with another plugin's published view works, including a computed column (`last_contact`);
  - an unpublished name, another plugin's internal table, a write to a view, and raw SQL on an internal table are all rejected.
  - Selecting a column that a view doesn't publish errors on Node. On Bun it returns the column name as a string, because Bun's SQLite treats unknown double-quoted names as text. No data leaks either way, and the layer 1 column check makes both runtimes fail the same way.

#### 3.3.2 Exposed operations

Each plugin declares its write operations, and the few read operations that carry logic. Plain cross-plugin reads use published views (§3.3.3).

```ts
ctx.expose({
  read: {
    projectStatus: { input: { project: "string", since: "date" }, output: ProjectStatusSchema, run: (i) => … },
    getContext:    { input: { project: "string" }, output: ContextSchema, run: (i) => … },
  },
  write: {
    addAction: { input: NewActionSchema, output: ActionSchema,
                 describe: (i) => `+ action "${i.title}"`, run: (i) => … },
    setHealth: { input: HealthSchema, output: HealthUpdateSchema,
                 describe: (i) => `~ ${i.code} health → ${i.health}`, run: (i) => … },
  },
})
```

- **Schemas.** Every operation has an input and an output schema, written in JSON Schema through a small builder in `@pm/api`. The kernel validates the input before `run` and the output after it (output only in tests). The owning plugin's business rules run inside `run`.
- **Calls.** `ctx.use("projects").read.projectStatus({ project: "CRM", since })` and `….write.addAction({...})`. Write calls from another plugin run in the caller's current transaction, or in a new one.
- **`describe(input)`** renders a write as one line for change sets and logs. It may show a before → after diff, using the plugin's own read operations.
- **Assistant tools come from this.** Every exposed operation becomes an assistant tool automatically: reads run directly, writes go into the change set. An operation can opt out with `assistant: false`, or set its own `toolDescription`.
- **CLI commands stay separate** (`ctx.command`), because their flags and human-readable output are designed per command. A command's `run` normally just calls the plugin's own exposed operations.
- **Compatibility.** Exposed operations are a plugin's public API. Adding operations or optional input fields is compatible. Removing or changing them needs a new plugin major version, and dependants declare a version range in `requires` (e.g. `requires: { projects: "^1" }`).

### 3.4 Extension points (UI and reports)

Plugins add UI through these named extension points, and through nothing else:

| Extension point | Example |
|---|---|
| `screen` | a top-level screen in the switcher and number keys (built-ins take `1`–`6`, external ones get `7`, `8`, … in load order) |
| `recordTab` (record type, tab) | a "Contracts" tab on project detail, a "Jira" tab on a project |
| `overviewPanel` | a panel on the Overview screen, with a priority for its position |
| `reportSection` (report, section) | a section in the project prep block, the board pack or the minutes |
| `field` (record type, field) | an extra field on a record, shown in Summary or detail, forms, `show --json` and `edit --<flag>`. The plugin stores the value in its own table |
| `listColumn` (list, column) | an extra column in Projects, People or Actions |
| `tagType` | an inbox tag prefix such as `$contract`, with a resolver. `#` and `@` are taken by projects and people |
| `quickAction` (record type) | an entry in a record's action menu (`.` key), with an optional direct key, e.g. "Create Jira ticket" |
| `globalAction` | a key that works on every screen and opens an overlay or side pane: inbox capture `i`, assistant `c`. Keys are claimed at load; a conflict skips the later plugin's action with a message |
| `statusBadge` | a short live indicator in the header, e.g. `● 3 new in inbox`, `● assistant` |
| `report` | a named report, e.g. `project-status`, `board`, `minutes`, that others can add `reportSection`s to; rendered by the kernel as md, text or json |
| `guideSection` | a Markdown section of the agent guide (`pm guide`) |
| `assistantProvider` | an AI provider implementing `AssistantProvider` (§7), selectable in `assistant.provider` |

- **Components.** UI extension points take Solid components. `@pm/api` gives plugins the same building blocks the built-ins use: `Panel`, `Table`, `Form`, `Field`, `KeyHints` and `useRecord`. Plugin screens therefore look and behave like the rest of pm.
- **Keyboard and focus.** pm owns the global keys. A plugin component receives keys only while it has focus, and declares its keys in the status bar through `KeyHints`.
- **Stability.** Every extension point is part of `apiVersion` 1. Adding an extension point or an optional field is compatible. Removing or changing one raises `apiVersion`.

### 3.5 Change sets

Every write through the assistant, and every plugin `quickAction` marked `confirm`, goes through the kernel's change set:
1. Each proposed operation is a call to an exposed **write** operation: `{ plugin, operation, input }`. Its line comes from that operation's `describe(input)`.
2. The TUI shows the list of operations.
3. The accepted operations run in **one transaction**, through the owning plugins' write operations. If any of them throws, the whole set is rolled back and the error is shown next to the failing line.
4. Applied change sets are logged in kernel tables (`kernel_change_set`, `kernel_change_set_op`) with their origin: assistant, quick action or inbox item.

### 3.6 Shared modules and the plugin build

A plugin must use **pm's own** instances of `solid-js`, `solid-js/store`, `@opentui/solid`, `@opentui/core` and `@pm/api`. Two Solid copies is a known cause of UIs that stop updating; the spike used one shared instance and didn't test the duplicate case.

- At startup, the kernel puts those module objects on `globalThis.__PM_MODULES__`.
- `pm plugin build [dir]` compiles the plugin's `src/` to `dist/` with the same Babel setup as pm's Node build: `babel-preset-solid`, universal mode, `moduleName: "@opentui/solid"`. It rewrites imports of the shared modules to generated shim files in `dist/__pm/`. Each shim re-exports the host's module, and fails with a clear message if the plugin is loaded outside pm.
- The output is plain ESM JavaScript, so one build runs on Bun and on Node. Plugins don't need OpenTUI's Bun-only runtime-plugin loader.
- Shims are generated from the host's export list at build time. A plugin built against an older pm that uses an export which has since been removed fails at load with a "rebuild the plugin" message. This is covered by failure isolation (§3.2).

### 3.7 Plugin commands

```
pm plugin list                  # id, version, source (built-in/folder/npm), status (ok/failed/disabled), error
pm plugin add <npm-name|path|tgz>   # runs `npm install` in ~/.pm/plugins (creates its package.json if needed)
pm plugin remove <id>           # npm uninstall or remove the folder; the plugin's tables stay unless --purge-data --yes
pm plugin enable|disable <id>   # edits plugins.disabled in config
pm plugin build [dir]           # build a plugin for development
pm plugin new <id>              # scaffold a plugin folder with an example screen, tab, command and test
```

`pm plugin add` needs `npm` on the PATH. Under Bun it uses `bun add --cwd ~/.pm/plugins` when npm is missing.

**Trust.** Plugins run in pm's process with full access to your files and data, like any npm package. pm warns on the first `pm plugin add` from a source that isn't built in. There's no sandbox.

### 3.8 Where the built-ins fit

The rest of this document describes the built-in plugins:
- §4 data model: tables owned by `projects`, `people`, `meetings` and `inbox`;
- §5 inbox: the `inbox` plugin;
- §6 CLI: commands registered by each plugin, plus kernel conventions;
- §7 assistant: the `assistant` plugin, whose tools come from every plugin's `ctx.tool`;
- §8 meetings: the `meetings` plugin, whose prep blocks are assembled from `reportSection`s;
- §9 TUI: kernel frame plus each plugin's screens, tabs and panels.

The full per-plugin reference (tables, exposed operations, CLI, extension points) is in [`2026-11-13-pm-plugins.md`](2026-11-13-pm-plugins.md).

**Hard and soft references.**
- `requires` is for plugins whose exposed operations a plugin can't work without.
- `reads` is for published views it uses.
- A plugin may store a **soft reference** to another plugin's record as a plain ID column. Soft references are shown by joining the other plugin's **published view**, or through `recordType` labels, never through its internal tables. If the owning plugin is disabled, they show as "unavailable" and are left untouched. This keeps the dependency graph acyclic:

| Plugin | Requires | Reads (views) | Owns (tables in §4) | Soft references |
|---|---|---|---|---|
| `people` | — | `projects.involvement`, `projects.project` | person, note, goal | note → project |
| `projects` | `people` | `people.person`, `meetings.meeting` | project, health_update, milestone, deliverable, risk, decision, action, involvement | owners, `for` and involvement → person (validated with `people.person`); action/decision → meeting |
| `meetings` | `projects`, `people` | `people.person`, `projects.project` | meeting, attendee, agenda_item | attendee → person; agenda item → project |
| `inbox` | — | — (labels through record types) | inbox_item, inbox_link | links → any record type |
| `assistant` | — | all published views, as tools | — (session state only) | — |

- `involvement` belongs to `projects`, because it depends on both a person and a project. `projects` shows a person's "Projects & roles" through a `recordTab` on the person record type. That's the kind of extension an external plugin would make.
- `inbox` resolves `#` and `@` through the `tagType`s that `projects` and `people` register. It doesn't know about either plugin.
- `assistant` collects its tools from all plugins.
- **The Overview screen belongs to the kernel.** All of its panels are `overviewPanel`s: overdue actions and the others come from `projects`, stakeholders to contact from `people`, and the inbox count from `inbox`.

## 4. Data model

Tables are grouped by the built-in plugin that owns them; §3.8 has the ownership table. Names here are the short names the plugins use. Physically they're prefixed with the plugin ID (§3.3.1). Every table has `id INTEGER PRIMARY KEY`, plus `created_at` and `updated_at` as ISO timestamps. Dates are calendar dates stored as `YYYY-MM-DD`, with no times or time zones. The schema is versioned, and migrations run on startup (see §10).

**Display IDs** add a prefix to the number:

| Prefix | Record |
|---|---|
| `A-` | action |
| `R-` | risk/issue |
| `D-` | deliverable |
| `DE-` | decision |
| `MS-` | milestone |
| `M-` | meeting |
| `I-` | inbox item |
| `N-` | note |
| `G-` | goal |

Inputs accept the ID with or without the prefix. Projects are referenced by **code** and people by **handle**.

**Archiving.** Projects and people are archived (`archived_at`), never deleted. Other records can be deleted.

### People

**person**

| Field | Values and rules |
|---|---|
| `handle` | unique, `[a-z0-9-]+`; defaults to the lowercased first name and gets a digit suffix if that's taken |
| `name` | |

## 5. Inbox and tagging

- **Syntax.** `#CODE` tags a project and `@handle` tags a person. Tags match case-insensitively. When an item is saved, resolved tags become `inbox_link` rows. An unresolved tag stays in the text and goes into `unresolved_tags`. An item with unresolved tags is still saved.
- **Capture.**
  - TUI: `i` on any screen opens the capture overlay, with autocomplete after `#` and `@`. If you're on a project or a person, their tag is pre-filled. Enter saves, Shift+Enter adds a new line, Esc cancels.
  - CLI: `pm inbox add "<text>"`.
- **Processing.**
  - *By an agent through the CLI.* Copilot in your editor, for example: run `pm inbox list --new --json`, create records with `--from-inbox I-n`, then `pm inbox done I-n --summary "…"`.
  - *Inside pm.* `P` on the Inbox screen gives the new items to the assistant (§7).
  - *By hand.* `p` turns an item into an action, note, decision, risk or health update, prefilled with the text and tags.
  - `z` dismisses an item. `u` reopens a processed or dismissed item.
- **Traceability.** The kernel records provenance (§4, Inbox). The Inbox screen lists, under each processed item, the records created from it.

## 6. CLI

The pattern is `pm <thing> <verb> [args] [--flags]`. The things are: `project`, `milestone`, `deliverable`, `risk`, `decision`, `action`, `person`, `note`, `goal`, `meeting`, `inbox`, `report`, `guide`. The verbs are `list`, `show`, `add`, `edit`, plus the ones that make sense for each thing: `done`, `archive`, `delete`, `close`, `dismiss`, `agenda add|move|remove`, `context`. Examples:

```
pm project add CRM "CRM replatforming" --effort 220
pm project edit CRM --health amber --health-comment "Design slipping 2 weeks"   # creates a health_update
pm project context CRM [--set-file ctx.md | --stdin]
pm action add "Send roadmap" --project CRM --for peter --due fri
pm action list --open --overdue
pm action list --owner anna --open
pm risk add CRM "Vendor delay" --type risk --severity high --owner bob
pm note add peter --interaction "Worried about budget" --project CRM
pm meeting add "Steering committee Q4" --date 2026-12-04 --kind steering --attendees peter,marie --projects CRM,ERP
pm meeting agenda M-4 add "Budget" --project CRM --ask "Release contingency"
pm report board M-4 --format md > board.md
pm guide                       # prints the usage guide for agents
```

**Rules**

- **JSON.** `--json` works on every command. `list` returns an array. `show`, `add` and `edit` return the full record, including its display ID. Errors return `{"error":{"code","message","hint"}}`.
- **No prompts.** Commands never ask for input. `delete` requires `--yes`.
- **Exit codes.** `0` OK, `1` validation error, `2` not found, `3` conflict or locked database. Messages say how to fix the problem, e.g. `unknown person "ana" — did you mean "anna"?`.
- **Dates.** Inputs accept `YYYY-MM-DD`, `today`, `tomorrow`, `+Nd`, `+Nw`, and weekday names (`mon` to `sun`, meaning the next such day after today). Output is always ISO.
- **References.** A person can be given as a handle, a project as a code or an ID, and any record as its display ID or a bare number.
- **Help.** `pm help` and `pm <thing> --help` list every flag.
- **Agent guide.** `pm guide` prints a Markdown guide, made by the kernel from every plugin's `guideSection` in dependency order. It covers what pm is, the most useful commands, the inbox-processing rules (concern → stakeholder note, "X will do Y" → action, "decided" → decision, "finished" → deliverable status, health signals → health update), and the rule to ask the user when something is ambiguous instead of guessing. `pm guide --write <path>` writes the guide to a file, for example the user's Copilot instructions file.

## 7. Assistant (pluggable; GitHub Copilot SDK first)

```
src/plugins/assistant/session.ts             chat loop and context; provider-independent
src/plugins/assistant/pane.tsx               chat pane and change-set review UI
src/plugins/assistant/providers/copilot.ts   adapter over @github/copilot-sdk
```

The tools aren't defined here. They're generated from every plugin's exposed operations (§3.3.2), plus any extra `ctx.tool`s, so an external plugin's data is automatically available to the assistant, within what that plugin exposes. Change sets are a kernel service (§3.5).

Providers are pluggable in two ways. Built-in providers live in `providers/`. External plugins can add one through the `assistantProvider` extension point (§3.4).

```ts
interface AssistantProvider {
  id: string
  checkAuth(): Promise<{ ok: true } | { ok: false; howToFix: string }>
  startSession(opts: { instructions: string; tools: ToolDef[] }): Promise<ProviderSession>
}
interface ProviderSession {
  send(message: string, context: Context): AsyncIterable<AssistantEvent> // text | toolCall | done | error
  cancel(): void
  close(): Promise<void>
}
```

- **Read tools** run straight away. They're the exposed read operations (project status, reports, context) and one query tool per published view (filter, sort, limit).
- **Write tools** are the exposed write operations, and they don't write directly. They append to a **pending change set**. pm shows each change (`+ action …`, `~ milestone due 26 Nov → 10 Dec`). You accept all with `y`, step through them with `Enter`, or reject with `n`. Accepted changes are applied in one transaction through the owning plugins' services (§3.5).
- **Context.** Each message carries the current screen and the selected record's key fields.
- **Instructions.** The session's instructions are the same text as `pm guide`.
- **TUI pane.** `c` opens or focuses a chat pane on the right. While the pane is focused, Esc returns focus to the main area. The pane can be zoomed to full width (`Z`) or hidden (`C`); hiding keeps the session. While a session is running, the header shows `● assistant`.
- **Inbox processing in pm.** `P` processes new inbox items one at a time: one change set per item, and once accepted the item is marked processed with a summary.
- **Loading.** The provider is loaded with a dynamic import only when the pane opens. `@github/copilot-sdk` is an `optionalDependency`. If it's missing, signed out or not allowed, the pane shows the `howToFix` text and the rest of pm is unaffected. `assistant.provider = "none"` hides the pane.
- **Authentication (Copilot).** It uses the user's own Copilot subscription, through the stored login of the bundled Copilot CLI, or `GITHUB_TOKEN` / a configured token. The organisation's Copilot policy must allow CLI usage.
- **Risk.** The SDK is in technical preview and targets Node. The assistant phase therefore starts with a spike (§12). If the SDK doesn't run under Bun, the pane is Node-only and shows "the assistant needs Node" under Bun.

## 8. Meetings and reports

- **Creating a meeting** with `--projects` (or picking projects in the TUI) adds an agenda item per project, "<name> status", with an empty `ask`.
- **The "since" date** for a project in a meeting is the first of these that exists:
  1. the meeting's `since_date`;
  2. the date of the most recent earlier *held* meeting that had an agenda item for that project;
  3. the meeting date minus 30 days.
- **The prep block** for a project is generated on demand and never stored. It contains, in this order:
  1. current health, with comment and date, and a warning if the last health update is older than "since";
  2. milestones completed since "since", plus open milestones due within 60 days after the meeting date, with late ones marked;
  3. deliverables that changed status since "since", or are due within 30 days;
  4. open risks and issues, high severity first;
  5. decisions since "since";
  6. overdue actions, plus open actions linked to the previous meeting;
  7. the agenda item's `ask`.
- **During the meeting.** The Notes tab holds the meeting notes. `a` adds an action and `D` a decision, both linked to the meeting and to the selected agenda item's project.
- **Closing.** `pm meeting close M-4` (TUI: `x`) sets the status to held and lists what was logged.
- **Reports.** Each report is a pure function of the data plus today's date:

| Command | Contents |
|---|---|
| `pm report status <project>` | the prep block, with "since" = 30 days ago |
| `pm report board <meeting>` | title, date, attendees, agenda with asks, then one prep block per covered project |
| `pm report minutes <meeting>` | attendees, notes, decisions and actions linked to the meeting |
| `pm report overview` | the Overview screen as text |

- **Formats.** `--format md` (default), `text` or `json`.
- **TUI export.** The Export tab previews the Markdown. `w` writes `<exportDir>/<date>-<slug>.md` and shows the path. `y` copies to the clipboard (OpenTUI clipboard / OSC 52).

## 10. Errors and data safety

- **Typed errors.** The kernel defines, and plugins throw, `ValidationError` (with a field), `NotFoundError` (with suggestions) and `ConflictError`. The CLI maps them to exit codes. The TUI shows them inline, or as a status-bar message for 5 seconds. A failure in a screen never crashes the app. The status bar shows the message and the screen keeps its last data.
- **First run.** The database directory and file are created. Migrations run per plugin, each in its own transaction. Before applying a migration to an existing database, the file is copied to `pm.db.bak-v<from>`.
- **Locked database.** `busy_timeout` handles short locks. Longer ones give exit code `3` in the CLI and a "database busy, retrying" message in the TUI.
- **Plugin failures** are isolated (§3.2): a broken plugin is skipped and reported, and pm keeps running. An exception thrown by a plugin's screen, tab or panel is caught by an error boundary around that component, which shows the error in place.
- **Assistant failures** (signed out, network, SDK errors) show only in the assistant pane.

## 11. Testing

- **Kernel**: plugin loading order, `requires` and cycles, version checks, failure isolation, migrations per plugin, change sets (including rollback when one operation fails), and record references.
- **Isolation**: on both runtimes, queries touching another plugin's table are rejected by layer 1 (joins, sub-queries, updates, aliases) and layer 2 (raw `sql`, a plugin-bundled Kysely). Published views can be read and joined but not written. Unpublished names and undeclared columns are rejected. A missing publisher gives `ViewUnavailableError`. The views used by a failed query must not leak into the next query. Migrations that create objects without the plugin's prefix, or triggers, are rolled back.
- **Built-in plugins**: `bun test` against a temporary database file per test, with an injectable "today". This covers queries, the "since" logic, prep blocks and reports.
- **CLI**: in-process runs that check stdout, JSON shape and exit codes.
- **TUI**: `testRender` frame tests per screen, plus the key flows: capture, create and edit, filter, accepting a change set.
- **Assistant**: a scripted fake provider that drives the session, the tools and the change sets. The Copilot provider gets a manual smoke checklist.
- **External plugins**: a fixture plugin in `test/fixtures/` is built with `pm plugin build`, loaded once from a folder and once from an `npm install` of its packed tarball, and exercised through a CLI command, a screen, a `recordTab` and a migration. This repeats the spike as a permanent test.
- **Node**: a smoke test that builds `dist-node/` and runs a few CLI commands plus the external-plugin test under Node 26.
- **CI**: add a job to `.gitlab-ci.yml` that runs type-checking, `bun test` and the Node smoke test, next to the existing SAST.

## 12. Phases

Each phase gets its own implementation plan.

1. **Kernel and CLI, with the `people`, `projects` and `inbox` plugins (data and CLI only).** Plugin host and registries (built-in loading only), SQLite adapter, the Kysely-based `ctx.data` with both isolation layers and kernel-managed transactions (confirm savepoints across plugin instances first), `ctx.publish` (published views) and `ctx.expose`/`ctx.use`, per-plugin migrations, change sets, record types, date parsing, the CLI dispatcher and conventions; the three plugins' tables, services, commands, `report status|overview`, and `pm guide`. After this phase Copilot in the editor can already use pm.
2. **TUI kernel and the projects UI.** Frame and switcher, forms, live refresh, error boundaries, the extension points `screen`, `recordTab`, `overviewPanel`, `listColumn` and `field`, the `@pm/api` UI building blocks; Overview, Projects and project detail (including Context), Actions, quick capture, and Inbox.
3. **People UI.** The People screen, notes, goals, the stakeholder fields and sorting, and the "Projects & roles" `recordTab`.
4. **Meetings plugin.** Agenda, prep blocks assembled from `reportSection`s, notes, close, `report board|minutes`, and export.
5. **External plugins.** Loading from `~/.pm/plugins` (folders and npm prefix), version checks, failure isolation for external code, shared-module shims, `pm plugin build|add|remove|list|enable|disable|new`, the `tagType` and `quickAction` extension points, and the fixture-plugin test on both runtimes.
6. **Assistant plugin.** First a spike: Copilot SDK sign-in with the user's work account, and running under Bun and Node. Then the provider interface, tools, change sets, the Copilot provider, the chat pane, and inbox processing inside pm.

## 13. Out of scope

- multiple users, sharing, sync or a server;
- importing from Excel or other tools;
- time tracking and per-person allocation (effort is one estimate per project);
- approval or sign-off of deliverables;
- a registry of recurring meetings;
- Word or PowerPoint export (Markdown only);
- the MCP integration that will fill project context (only the field and its CLI are in scope);
- assistant providers other than Copilot (only the interface is in scope);
- a plugin marketplace or registry beyond npm itself, plugin sandboxing, and plugin settings screens;
- any specific external plugin (Jira, calendar, budgets…); only the API and the fixture plugin are in scope.
